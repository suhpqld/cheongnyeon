## A. GitHub (PM, 가장 먼저)

저장소: `https://github.com/suhpqld/cheongnyeon`

### A-1. 저장소를 공개로 바꾸기 (꼭 지금)
- 이유 1: **Vercel 무료(Hobby) 요금제는 비공개 저장소에서 팀원이 올린 커밋을 배포하지 않는다.** ("The Hobby Plan does not support collaboration for private repositories" 오류로 배포가 막힘) 공개 저장소면 된다.
- 이유 2: 최종 제출물이 **공개 GitHub 저장소**다.
- 방법: 저장소 → **Settings** → 맨 아래 **Danger Zone** → **Change repository visibility** → **Public** → 확인
- 공개라서 `.env.local`이 절대 올라가면 안 된다 (D, F에서 확인).

### A-2. 팀원 초대
- 저장소 → **Settings** → **Collaborators** → **Add people** → 팀원 GitHub 아이디 4명 (임채희, 이건희, 김효은, 김예은)
- 팀원은 GitHub 알림이나 이메일에서 **초대 수락**을 눌러야 push할 수 있다. 디스코드에 "초대 메일 수락해 주세요" 공지.

### A-3. 저장소에 Next.js 코드가 있는지 확인
- 저장소 첫 화면에 `package.json`, `app` (또는 `src/app`) 폴더가 보이면 된다.
- **비어 있으면**: PM 컴퓨터에서 아침에 만든 Next.js 프로젝트를 먼저 올린다.
  ```
  cd cheongnyeon
  git add .
  git commit -m "chore: Next.js 프로젝트 시작"
  git branch -M main
  git push -u origin main
  ```

### A-4. 문서 묶음 올리기
- (A-6보다 먼저 해도 되고 나중에 해도 된다. PM은 규칙을 건너뛸 수 있다)
- `복냥이_개발문서.zip`을 풀어서 저장소 맨 위에 넣는다: `CLAUDE.md`, `AGENTS.md`, `.claude/settings.json`, `docs/` (`.claude`는 점으로 시작하는 숨은 폴더라 Finder에서 안 보일 수 있다. Mac은 `Cmd + Shift + .`로 보인다)
- 예전 `PRD.md`가 있으면 지운다.
- PM은 main에 직접 올릴 수 있다. 자기 AI에게 **"커밋하고 푸시해줘"**(→ `chore/pm-docs` 브랜치에 올라감) 다음 **"chore/pm-docs main에 합쳐줘"**. 직접 하려면:
  ```
  git switch -c chore/pm-docs
  git add CLAUDE.md AGENTS.md .claude/settings.json docs
  git rm --cached PRD.md   # PRD.md가 저장소에 있었으면
  git commit -m "docs: 기능별 개발 문서와 작업 규칙"
  git switch main && git pull --no-rebase origin main
  git merge --no-ff chore/pm-docs -m "merge: chore/pm-docs"
  git push origin main
  ```
- 디스코드에 공지: "문서 올렸어요. `git pull` 하고 docs/08 F부터 해 주세요."

### A-5. 디스코드
- 팀 채널 하나를 "보고" 용으로 정한다. AI가 주는 보고 문장은 여기에 올린다. PM은 이 채널을 보고 main에 합친다.
- **키(.env.local)는 채널이 아니라 개인 메시지로** 보낸다.

### A-6. main 보호 규칙 (PM만 main에 올리게)
AI 규칙(CLAUDE.md)만 믿지 않고 GitHub에서도 막는다. 공개 저장소라 무료로 된다.
1. 저장소 → **Settings** → 왼쪽 **Rules** → **Rulesets** → **New ruleset** → **New branch ruleset**
2. Ruleset Name: `main 보호` / Enforcement status: **Active**
3. **Bypass list** → **Add bypass** → **Repository admin** (저장소 주인인 PM이 여기에 해당) → 모드를 고르라면 **Always allow**
4. **Target branches** → **Add target** → **Include default branch** (main)
5. Rules에서 켜기: ✅ **Restrict updates** (bypass 목록만 push 가능), ✅ **Restrict deletions**, ✅ **Block force pushes**. 나머지는 끈 채로 둔다.
6. **Create**
- 확인: 팀원 한 명이 main에 push해 보면 `GH013: Repository rule violations`로 거절된다. 이게 정상이다.
- 팀원은 Collaborator(쓰기 권한)라서 브랜치 push는 된다. **Admin 권한을 주지 않는다** (주면 main에도 push 가능).
- GitHub 웹의 PR "Merge" 버튼은 이 규칙 때문에 막힐 수 있다. PM도 AI에게 "main에 합쳐줘"로 합친다 (CLAUDE.md 4장).

## B. Supabase (PM 또는 01 담당)

### B-1. 프로젝트 상태
- supabase.com 로그인 → 프로젝트 열기. 위에 **Paused**가 보이면 **Restore**.
- 리전: 서울(ap-northeast-2)로 만들었는지 (Project Settings → General)

### B-2. SQL 실행 (01이 기다리지 않게 PM이 먼저)
SQL은 `docs/01_기반_뼈대.md`의 "P0-2. DB"에 전부 있다. 왼쪽 메뉴 **SQL Editor** → **New query** → 붙여 넣기 → **Run**. 순서대로:
1. **Table Editor에 테이블이 하나라도 있으면** (아침에 예전 PRD.md SQL을 돌렸으면) `reset.sql` 먼저. "destructive operation" 경고가 나오면 확인을 누른다. (시연용 데이터뿐이라 지워도 된다)
2. `schema.sql`
3. `seed.sql`
4. 확인 쿼리:
   ```sql
   select
     (select count(*) from form_field) as fields,
     (select count(*) from document_rule) as rules,
     (select count(*) from precheck_rule) as prechecks,
     (select count(*) from pg_tables where schemaname = 'public' and rowsecurity) as rls_tables;
   ```
   **18, 16, 7, 10**이 나오면 성공.
- Security Advisor에 "RLS enabled, no policy" 경고가 보여도 **정상**이다. 일부러 정책을 두지 않았다 (서버만 비밀 키로 접근).

### B-3. 값 두 개 복사 (D에서 씀)
| 값 | 어디서 | `.env.local` 이름 |
|---|---|---|
| Project URL (`https://xxxx.supabase.co`) | Project Settings → **Data API** (또는 대시보드 위쪽 **Connect** 버튼) | `NEXT_PUBLIC_SUPABASE_URL` |
| **secret 키** (`sb_secret_...`) | Project Settings → **API Keys** → secret keys에서 보기와 복사. 없으면 새로 만들기. 화면이 다르면 **Legacy API Keys** 탭의 `service_role` 키 | `SUPABASE_SECRET_KEY` |
- secret 키는 **DB 전체를 마음대로 읽고 쓰는 열쇠**다. 디스코드 채널, GitHub, 브라우저 코드, `NEXT_PUBLIC_`로 시작하는 변수에 절대 넣지 않는다.
- anon(publishable) 키는 이제 쓰지 않는다.

## C. OpenRouter (PM 또는 이건희)

1. openrouter.ai 로그인
2. **Credits**: 잔액 확인. 0이면 5~10달러 충전 (기본 모델 `google/gemini-2.5-flash`는 유료지만 아주 싸다. 하루 시연에 1달러도 안 나올 가능성이 크다)
3. **Keys**: 지금 쓰는 키에 **사용 한도**(예: 5달러)를 걸어 둔다. 키가 새도 피해가 작다. 새로 만들면 D의 값도 바꾼다.
4. **모델 확인**: Models에서 `google/gemini-2.5-flash` 검색 → 지금 쓸 수 있는지, 입력에 image가 되는지 본다. 안 보이면 비슷한 최신 Flash 모델 이름을 `OPENROUTER_MODEL`, `OPENROUTER_VISION_MODEL`에 넣는다.
5. 연결 시험 (Mac 터미널, cheongnyeon 폴더에서. 키가 화면이나 기록에 찍히지 않게 파일에서 읽음):
   ```
   set -a; source .env.local; set +a
   curl -s https://openrouter.ai/api/v1/chat/completions \
     -H "Authorization: Bearer $OPENROUTER_API_KEY" \
     -H "Content-Type: application/json" \
     -d '{"model":"google/gemini-2.5-flash","messages":[{"role":"user","content":"안녕이라고만 답해"}]}'
   ```
   응답에 `"content":"안녕"` 비슷한 게 있으면 성공. `401`은 키 문제, `402`는 잔액 부족.

## D. `.env.local` 만들어 나눠 주기 (PM)

cheongnyeon 폴더 맨 위에 `.env.local` (파일 이름 그대로, 확장자 없음):
```
NEXT_PUBLIC_SUPABASE_URL=https://xxxx.supabase.co
SUPABASE_SECRET_KEY=sb_secret_xxxxxxxx
OPENROUTER_API_KEY=sk-or-v1-xxxxxxxx
OPENROUTER_MODEL=google/gemini-2.5-flash
OPENROUTER_VISION_MODEL=google/gemini-2.5-flash
DEMO_MODE=false
```
- `=` 앞뒤에 띄어쓰기 없이, 따옴표 없이
- **확인**: 터미널에서 `git check-ignore .env.local` → `.env.local`이 출력되면 GitHub에 안 올라간다. 아무것도 안 나오면 `.gitignore`에 `.env*`와 `!.env.example` 두 줄을 넣는다.
- 디스코드 **개인 메시지**로 팀원 4명에게 파일 내용을 보낸다.
- Windows 메모장으로 저장하면 `.env.local.txt`가 되기 쉽다. "파일 형식: 모든 파일"로 저장한다.
- 값을 바꾸면 (OPENROUTER 모델 등) 다시 나눠 주고, 각자 `npm run dev`를 껐다 켠다.

## E. Vercel (PM)

### E-1. 프로젝트 연결 확인
- vercel.com → 프로젝트 목록에 cheongnyeon이 있으면 E-2로.
- 없으면 **Add New → Project → cheongnyeon Import**
  - 팀 선택에서 **개인 계정(Hobby)**. **Pro Trial은 누르지 않는다.**
  - **Framework Preset이 Next.js**로 자동으로 떠야 한다. Other로 나오면 저장소에 코드가 없거나 한 폴더 안에 들어가 있는 것 → A-3 확인, 또는 **Root Directory**를 그 폴더로.

### E-2. 환경 변수
- 프로젝트 → **Settings → Environment Variables** → D의 6개를 하나씩 (Production, Preview, Development 모두 체크)
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`는 지워도 되고 둬도 된다.
- **넣거나 바꾼 뒤에는 꼭 Redeploy**: Deployments → 맨 위 배포 → 오른쪽 `⋯` → **Redeploy**

### E-3. 자동 배포 확인
- Settings → Git → Production Branch가 **main**인지
- main에 push될 때마다 1~2분 뒤 자동 배포된다. 팀원 브랜치도 push하면 미리보기 배포가 따로 만들어진다.
- PM 팁: 합치기 전에 GitHub 저장소의 **Branches** 화면이나 커밋 옆 표시(✓ 초록, ✗ 빨강)로 그 브랜치의 Vercel 미리보기 build가 성공했는지 볼 수 있다.
- **시연과 시험은 Production 주소**(`https://cheongnyeon-....vercel.app`, Deployments에서 Production 표시가 있는 것의 Domains)로 한다. 브랜치 미리보기 주소는 Vercel 로그인을 요구할 수 있다.

### E-4. 배포가 실패하면
- Deployments → 빨간 배포 → **Build Logs** 맨 아래 오류를 복사해서, 그 커밋을 올린 사람의 AI에게 붙여 넣고 "이 오류 고쳐줘"
- **"Deployment Blocked ... does not support collaboration for private repositories"** → A-1(공개 전환)을 안 한 것. 공개로 바꾸고 Redeploy.
- **"could not associate the committer with a GitHub user"** → 그 사람의 git 이메일이 GitHub 계정 이메일과 다른 것 → F-2

## F. 각자 컴퓨터 (모두, A가 끝나면 바로)

### F-1. Node
- `node -v` → **v20 이상**이면 된다. 낮으면 nodejs.org에서 LTS 설치 후 터미널을 다시 연다.

### F-2. git 이름과 이메일
```
git --version
git config --global user.name "홍길동"
git config --global user.email "GitHub에 등록된 이메일"
```
- 이메일은 **GitHub 계정에 등록된 이메일**이어야 한다 (GitHub → Settings → Emails에서 확인). 다르면 Vercel이 배포를 막는다 (E-4).

### F-3. GitHub 로그인 (push가 되게)
- GitHub CLI로 하는 게 가장 쉽다:
  - Mac: `brew install gh` / Windows: `winget install --id GitHub.cli`
  - `gh auth login` → GitHub.com → HTTPS → "Authenticate Git with your GitHub credentials?" **Yes** → Login with a web browser → 화면의 코드를 브라우저에 입력
  - 확인: `gh auth status` → Logged in
- gh를 못 깔면: 처음 `git push`할 때 뜨는 브라우저 로그인 창으로 로그인한다. Mac에서 비밀번호를 물으면 GitHub 비밀번호가 아니라 **Personal Access Token**을 넣어야 한다 (GitHub → Settings → Developer settings → Tokens).
- A-2 초대를 수락했는지 확인 (안 하면 push가 403).

### F-4. 받아서 실행
```
git clone https://github.com/suhpqld/cheongnyeon.git
cd cheongnyeon
npm install
```
- PM이 보낸 `.env.local`을 cheongnyeon 폴더 맨 위에 만든다 (D)
- `git check-ignore .env.local` → `.env.local`이 출력되는지 확인
- `npm run dev` → 브라우저에서 `http://localhost:3000` 이 열리면 성공 → `Ctrl + C`로 끔

### F-5. AI 준비
- **Claude Code**: cheongnyeon 폴더에서 연다 (터미널이면 `cd cheongnyeon` 후 `claude`). 처음 열 때 폴더를 믿겠냐고 물으면 허용한다.
  - `/permissions`를 쳐서 `.claude/settings.json`의 규칙(git, build 허용, force push 금지)이 보이는지 확인
  - `CLAUDE.md`는 자동으로 읽힌다
- **Cursor 등 다른 AI**: 같은 폴더를 열면 `AGENTS.md`를 읽는다. 안 읽는 것 같으면 첫 메시지에 "CLAUDE.md와 docs/00을 먼저 읽어"를 붙인다.

### F-6. 시작
- AI에게: **"나 docs/0X_....md 만들 거야"** (자기 담당 파일)
- 중간 저장이나 다 됐을 때: **"커밋하고 푸시해줘"** → **내 브랜치에만** 올라간다. AI가 준 보고 문장을 디스코드에 올리면 **PM이 main에 합친다.**
- PM이 "main에 합쳤어요"라고 하면: **"최신 main 받아줘"**
- PM이 "충돌 나서 못 합쳤어요"라고 하면: **"main 받아서 충돌 고쳐줘"** → 다시 "커밋하고 푸시해줘"

### 푸시가 안 될 때
| 메시지 | 원인 | 할 일 |
|---|---|---|
| `Permission denied`, `403` | 초대 미수락, 로그인 안 함 | A-2 수락, F-3 |
| `Authentication failed` | 비밀번호로 로그인 시도 | F-3 (gh 또는 토큰) |
| `GH013`, `Repository rule violations` | main에 올리려고 함 (팀원은 못 함) | 정상. AI에게 "내 브랜치에 올려줘" 하고 PM에게 부탁 |
| `rejected ... fetch first` | 내 브랜치에 다른 컴퓨터에서 올린 커밋이 있음 | AI에게 "다시 푸시해줘" (CLAUDE.md 2장 6단계가 받아서 다시 올림) |
| `CONFLICT` | 같은 파일을 둘이 고침 | AI가 멈추고 누구 파일인지 알려 줌 → 그 사람과 디스코드로 정리 |
| `npm run build` 실패 | 코드 오류 | AI에게 "build 오류 고쳐줘". 급하면 그대로 "커밋하고 푸시해줘" (wip로 올라가고, PM에게는 아직 합쳐 달라고 하지 않음) |
