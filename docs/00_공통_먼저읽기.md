# 00 공통 약속 (모두 먼저 읽기)

> **AI에게:** 기능 파일을 만들기 전에 이 문서를 끝까지 읽는다. 여기 적힌 이름, 타입, API 모양, 파일 주인은 다섯 명이 동시에 개발하기 위한 **약속**이라 바꾸지 않는다. 바꿔야 할 것 같으면 멈추고 사람에게 말한다.

---

## 0. 사람용: 이 문서 묶음 쓰는 법

1. PM이 `docs/` 폴더, `CLAUDE.md`, `AGENTS.md`, `.claude/settings.json`을 저장소 main에 올린다. 예전 `PRD.md`가 있으면 지운다. (이 문서들로 바뀌었다)
2. 각자 `git pull origin main`
3. 자기 AI(Claude Code, Cursor 등)에게 말한다: **"나 docs/04_제출준비카드.md 만들 거야"**
4. AI가 00과 기능 파일을 읽고, 브랜치를 만들고, P0부터 만든다.
5. **01 기반이 main에 들어오기 전에는** 기능 파일의 "01 전에 할 수 있는 일"만 한다.
6. 중간중간, 그리고 다 되면 AI에게 **"커밋하고 푸시해줘"** → AI가 **내 브랜치에만** 올리고 보고 문장을 준다 → 디스코드에 올린다.
7. **main에는 PM(박수홍)만 합친다.** PM이 합쳤다고 공지하면 각자 AI에게 **"최신 main 받아줘"**.

## 1. 복냥이 한눈에

- **이름:** 복냥이: 어려운 복지 서류, 이제 나한테 말하면 된다냥
- **한 줄:** 말로 대답하면 복지 신청서 내용이 정리되고, 추가 서류 요청은 사진 한 장으로 풀어 주어서, **복지 신청을 끝까지 마치게 돕는** 웹앱.
- **첫 대상 제도:** 서울형 기초보장제도 (구조는 모든 제도로 넓힐 수 있게: **제도 = 데이터**)
- **주 사용 장면 (피드백 반영):** 어르신 혼자보다 **자녀가 옆에서 함께** 쓰거나, **주민센터나 디지털배움터에서 도우미와 함께** 쓰는 장면을 주 시나리오로 한다. 어르신 혼자 쓰는 것도 된다.

### 핵심 기능 세 개
| 막히는 지점 | 기능 | 화면 이름 (사용자에게 보이는 이름) |
|---|---|---|
| 신청서 작성 | ① 말로 채우는 신청서 | 질문, 확인 |
| 서류 준비 | ② 제출 준비 카드 + 옮겨 쓰는 카드 + 내기 전 점검 | 제출 준비 카드 |
| 보완 요청 | ③ 추가 서류 정리 | **추가로 챙길 서류** |

## 2. 원칙 (모든 기능에 적용)

1. **AI가 읽고, 코드가 계산한다.** AI는 말과 사진을 JSON으로 바꾸고 쉬운 말을 쓴다. 다음 질문, 필수 칸 검사, 서류 목록, 대조, 기한 계산, 상태 변경은 코드가 규칙으로 한다.
2. **수급 여부를 판정하지 않는다.** "받을 수 있어요", "대상이에요", "탈락이에요", 예상 금액을 화면과 AI 출력에 절대 쓰지 않는다. 결과 화면마다 다음 문장을 둔다:
   > 복냥이는 신청을 도와요. 받을 수 있는지는 구청에서 조사해서 정해요.
3. **틀린 값이 신청서에 그대로 들어가지 않게 한다.** 모르는 값은 "확인 필요"로, 대충 말한 금액은 "약 30만 원 (확인 필요)"로 표시하고, 어디서 확인하는지 알려 준다.
4. **AI가 읽은 내용은 원문과 함께 보여 준다.** 기한과 서류 이름은 사용자가 원문과 비교해서 확인한다.
5. **개인정보는 최소로.** 이름, 주민등록번호, 상세 주소, 전화번호는 DB에 저장하지 않는다. 보완 요청서 사진도 저장하지 않는다. 가족 공유 화면에는 금액과 답을 보여 주지 않는다.
6. **시연이 멈추지 않게.** AI가 실패해도 버튼과 글로 끝까지 갈 수 있어야 한다.

## 6. git 규칙

- **main에는 PM(박수홍)만 합친다.** 팀원은 자기 브랜치에만 push한다. (GitHub 규칙으로도 PM 말고는 main push가 막혀 있다. 08의 A-6)
- 브랜치 이름: `feat/01-base`, `feat/02-question`, `feat/03-voice-ai`, `feat/04-card`, `feat/05-extra`, `feat/06-status-share`, PM 문서는 `chore/pm-docs`
- 시작: `git switch main && git pull --no-rebase origin main && git switch -c feat/0X-...` (이미 있으면 `git switch feat/0X-...`). `package.json`이 바뀌었으면 `npm install`
- 커밋 메시지: `feat(04): 준비 카드 3칸 탭` 처럼 기능 번호를 붙인다. build가 안 되는 중간 저장은 `wip(04): ...`
- **커밋과 푸시는 사람이 말할 때만 한다.** 순서는 `CLAUDE.md`에 있다.
  | 사람이 하는 말 | AI가 하는 일 | CLAUDE.md |
  |---|---|---|
  | "커밋하고 푸시해줘" | 내 파일만 커밋 → build → 최신 main을 내 브랜치에 받기 → **내 브랜치에 push** → 디스코드 보고 문장 | 2장 |
  | "최신 main 받아줘" | PM이 합친 main을 내 브랜치에 받기, 충돌 풀기, 다시 push | 3장 |
  | (PM) "feat/04-card main에 합쳐줘" | 합쳐 보고 build 통과하면 main에 push, 실패하면 되돌리고 이유 보고 | 4-1 |
  | (PM) "브랜치 다 합쳐줘" | 01부터 06까지 차례로 합치고 결과 표 | 4-2 |
  | (PM) "브랜치 상태 보여줘" | 브랜치마다 새 커밋 수, 마지막 커밋 | 4-3 |
- 기능 파일의 "끝낼 때"는 "커밋하고 푸시해줘"로 **내 브랜치에 올리고 PM에게 합쳐 달라고 하는 것**까지다.
- main에 올라가면 Vercel이 자동 배포한다. **main은 항상 build가 되는 상태**여야 한다. (PM이 합칠 때 build를 확인한다)
- `.env.local`, `node_modules`, `.next`는 절대 커밋하지 않는다. force push, reset --hard, rebase는 하지 않는다.
- `.claude/settings.json`에 git과 build 명령을 미리 허용해 두었다 (Claude Code가 매번 묻지 않음). main으로 가는 push는 매번 묻고, force push와 `.env.local` 읽기는 막아 두었다.

## 7. 기술 스택, 환경 변수, 보안 구조

### 스택
| 영역 | 기술 |
|---|---|
| 화면, 서버 API | Next.js (App Router, TypeScript), Tailwind CSS |
| 배포 | Vercel (Hobby 무료, main 자동 배포) |
| DB | Supabase PostgreSQL, **RLS 켬**, 서버에서 비밀 키로만 접근 |
| AI | **Claude API** (Anthropic): 말 읽기 `claude-haiku-5-5`, 사진 읽기 `claude-sonnet-5-5`. 패키지 없이 `fetch`로 부름 |
| 음성 | 브라우저 Web Speech API (음성 인식, 읽어 주기) |
| 출력 | HTML 인쇄 화면 + 브라우저 인쇄 (PDF로 저장 가능). pdf-lib 안 씀 |
| 검사 | zod |

설치된 패키지 외에는 쓰지 않는다: `next`, `react`, `@supabase/supabase-js`, `zod`, Tailwind.

### 환경 변수 (`.env.local`과 Vercel에 같은 이름으로)
```
NEXT_PUBLIC_SUPABASE_URL=          # 이미 있음
SUPABASE_SECRET_KEY=               # 새로: Supabase Project Settings > API Keys의 secret 키 (sb_secret_...) 또는 Legacy의 service_role 키. 서버 전용
ANTHROPIC_API_KEY=                 # Claude API 키 (sk-ant-...). 서버 전용
CLAUDE_TEXT_MODEL=claude-haiku-5-5        # 말 읽기, 주민센터에서 할 말 (빨라야 함)
CLAUDE_VISION_MODEL=claude-sonnet-5-5     # 보완 요청서 사진 읽기 (정확해야 함, 05가 시험해서 바꿀 수 있음)
DEMO_MODE=false                    # true면 AI가 실패할 때 준비된 응답을 돌려줌 (발표용 안전장치)
```
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`는 이제 쓰지 않는다. (지워도 되고 그냥 둬도 됨)
- Vercel에 새 변수를 넣으면 **Redeploy** 해야 적용된다.

### 보안 구조 (피드백 반영)
```
브라우저 ── fetch + 헤더 x-app-token ──▶ Next.js API 라우트 ── 비밀 키 ──▶ Supabase (RLS 켬, 정책 없음)
                                          └─ Claude API 키 ──▶ Claude API (api.anthropic.com)
```
- 신청 건을 만들면 서버가 **접근 토큰**(32자 무작위)과 **이어서 하기 번호**(8자리 숫자)를 준다.
- 브라우저는 `{ appId, token, resumeCode }`를 localStorage `boknyang.session`에 둔다.
- `/api/apps/[id]/...`와 AI 라우트는 `x-app-token` 헤더가 그 신청 건의 토큰과 같아야 한다 (`requireApp`).
- 이어서 하기 번호로 토큰을 다시 받는 `/api/resume`은 **같은 IP에서 10분에 5번 틀리면 10분 잠금**.
- 가족 공유는 따로 만든 `share_code`(10자, 7일 만료, 멈출 수 있음)로 **보기 전용, 금액과 답 숨김** 화면만 연다.
- RLS를 켜고 정책을 두지 않으므로, anon 키로는 아무것도 못 읽는다.

## 10. 상태와 단계

### 상태 코드 (`application.status`)
| 코드 | 화면 표시 | 바뀌는 때 | 바꾸는 기능 |
|---|---|---|---|
| `drafting` | 신청서 쓰는 중 | 신청 건을 만들 때 | 01 (생성) |
| `preparing` | 서류 챙기는 중 | 확인 화면에서 "맞아요, 다음으로" | 02 |
| `submitted` | 주민센터에 냈어요 | 다녀왔어요에서 "서류를 다 냈어요", 추가 서류 화면에서 "추가 서류를 냈어요" | 06, 05 |
| `supplementing` | 추가 서류를 내야 해요 | 추가 서류 요청을 읽어서 저장했을 때 | 05 |

허용되는 변경 (서버가 검사, 아니면 409):
| 지금 | 다음 |
|---|---|
| drafting | preparing, supplementing |
| preparing | submitted, supplementing |
| submitted | supplementing |
| supplementing | submitted |

- `submitted`로 바뀔 때 `submitted_at`을 지금 시각으로 저장한다.
- **서류 준비 완료**는 상태가 아니라 계산 값이다: 체크리스트가 1개 이상이고 모두 `is_done`이면 참.

### 단계 표시 (StageTracker, 06이 만들고 여러 화면이 씀)
```
① 신청서 쓰기 ─ ② 서류 챙기기 ─ ③ 주민센터에 내기 ─ ④ 결과 기다리기
```
| 단계 | 끝났다고 보는 조건 | 끝났을 때 글 |
|---|---|---|
| ① | status가 drafting이 아님 | 신청서 다 썼어요 |
| ② | 서류 준비 완료 | **서류 준비 완료** |
| ③ | `submitted_at`이 있음 | **주민센터 제출 완료 (11월 21일)** |
| ④ | (진행 중일 때) status가 submitted | 결과 기다리는 중 |
- status가 supplementing이면 ③ 옆에 굵게 "추가 서류 D-7".
- 지금 단계는 굵은 테두리 + "지금" 글자. 색만으로 구분하지 않는다.

## 11. API 약속 (요청, 응답 모양)

- 모든 응답은 JSON. 실패는 `{ "error": "코드", "message": "쉬운 말" }` + 알맞은 HTTP 상태.
- `🔒` 표시는 헤더 `x-app-token` 필요 (`requireApp`). AI 라우트는 본문에 `appId`를 넣고 같은 헤더를 보낸다.
- DB 칸은 snake_case, API 응답은 camelCase (`toCamel` 사용).

## 12. 공통 타입 (`lib/types.ts`, 01이 이 내용 그대로 만든다)

```ts
// lib/types.ts — 01 기반이 만든다. 다른 기능은 import만 하고 고치지 않는다.

export type HelperMode = 'self' | 'family' | 'helper';
export type AppStatus = 'drafting' | 'preparing' | 'submitted' | 'supplementing';
export type FieldType = 'yes_no' | 'choice' | 'district' | 'count' | 'money' | 'text';
export type PlaceGroup = 'home' | 'onsite' | 'bank' | 'work' | 'tax' | 'gov24';
export type InputMethod = 'voice' | 'button' | 'text' | 'unknown';
export type AnswerValue = boolean | number | string; // 모름은 문자열 'unknown'
export type PrecheckResult = 'yes' | 'no' | 'unknown';

export interface Condition {
  field: string;
  op: 'eq' | 'neq' | 'in' | 'gt' | 'lt';
  value: unknown;
}
export type ShowIf = Condition | Condition[] | null;

export interface Program {
  id: string;
  code: string;
  name: string;
  summaryEasy: string;
  applyPlace: string;
  contact: string;
  afterSubmitEasy: string;
}

export interface FieldOption { value: string; label: string; }

export interface FormField {
  id: string;
  key: string;
  commonKey: string | null;
  label: string;            // 공식 신청서 칸 이름 (옮겨 쓰는 카드에 씀)
  section: string;          // 사는 곳, 가구, 집, 버는 돈, 재산, 신청 방법
  questionEasy: string;     // 본인에게 묻는 말
  questionHelper: string;   // 가족, 도우미가 볼 때 묻는 말 ("신청하시는 분은...")
  helpEasy: string | null;
  type: FieldType;
  options: FieldOption[] | null;
  required: boolean;
  allowUnknown: boolean;
  minValue: number | null;
  maxValue: number | null;
  showIf: ShowIf;
  confirmLabel: string | null; // 크게 확인할 때 앞말: "한 달 월세" + "25만 원"
  checkGuide: string | null;   // 모를 때 어디서 확인하는지
  sortOrder: number;
}

export interface Answer {
  fieldKey: string;
  value: AnswerValue;
  rawSpeech: string | null;
  inputMethod: InputMethod;
  isApproximate: boolean;
}
export type AnswerMap = Record<string, Answer>;

export interface Application {
  id: string;
  programId: string | null;
  status: AppStatus;
  helperMode: HelperMode;
  resumeCode: string;
  submittedAt: string | null;
  shareActive: boolean;
  createdAt: string;
  updatedAt: string;
}

export interface ChecklistItem {
  id: string;
  docName: string;
  easyExplain: string | null;
  issuePlace: string | null;
  placeGroup: PlaceGroup;
  source: 'base' | 'supplement';
  supplementId: string | null;
  dueDate: string | null;      // YYYY-MM-DD
  isDone: boolean;
  alsoRequested: boolean;      // 기본 목록에 있었는데 추가 요청에도 나온 서류
  createdAt: string;
}

export interface PrecheckRule {
  id: string;
  checkQuestion: string;
  whyEasy: string;
  fixEasy: string;
  relatedDoc: string | null;
  condition: ShowIf;
  sortOrder: number;
}

export interface ExtractRequest {
  appId: string;
  utterance: string;
  helperMode: HelperMode;
  field: Pick<FormField, 'key' | 'type' | 'questionEasy' | 'options' | 'allowUnknown' | 'minValue' | 'maxValue'>;
  otherFields: Pick<FormField, 'key' | 'type' | 'questionEasy' | 'options'>[];
  clarify: { question: string; options: { label: string; value: AnswerValue }[] } | null;
}

export interface ExtractResult {
  value: AnswerValue | null;
  confidence: 'high' | 'low';
  isApproximate: boolean;
  heardAs: string;
  clarifyQuestion: string | null;
  clarifyOptions: { label: string; value: AnswerValue }[] | null;
  otherValues: { key: string; value: AnswerValue; isApproximate: boolean }[];
}

export interface CardScriptRequest {
  appId: string;
  programName: string;
  helperMode: HelperMode;
  applicantType: string | null;       // self, family, other
  answerLines: string[];              // "같이 사는 사람: 1명 (혼자)"
  checkLabels: string[];              // 확인 필요한 칸 이름
  supplementItems: string[];          // 추가 서류를 내러 갈 때 서류 이름
}

export interface SupplementItem {
  name: string;           // 종이에 적힌 이름 그대로
  originalText: string;   // 그 서류가 적힌 원문 줄
  easyName: string;
  easyExplain: string;
  issuePlace: string;
  placeGroup: PlaceGroup;
}

export interface SupplementParsed {
  programName: string | null;
  items: SupplementItem[];
  deadline: string | null;              // YYYY-MM-DD
  deadlineOriginalText: string | null;  // "제출기한: 2026년 11월 28일까지"
  officeName: string | null;
  officeContact: string | null;
  hardWords: { word: string; easy: string }[];
  consequenceEasy: string | null;
  summaryEasy: string;
}

export interface Supplement {
  id: string;
  parsed: SupplementParsed;
  deadline: string | null;
  deadlineConfirmed: boolean;
  submittedAt: string | null;
  createdAt: string;
}

export interface Session {
  appId: string;
  token: string;
  resumeCode: string;
}
```

### 꼭 지킬 것 (디지털 포용)
- **한 화면에 하나.** 질문 하나, 주요 버튼 2~3개. (구 선택처럼 고르는 화면은 예외)
- **큰 글씨.** 기본 20px, 질문 28~32px 굵게, 줄 간격 1.6. "글씨 크게"를 켜면 기본 24px.
- **큰 버튼.** 높이 64px 이상, 간격 12px 이상, 둥근 모서리. 아이콘만 있는 버튼 금지 (항상 글자 함께).
- **높은 대비.** 4.5:1 이상. 흐린 회색 글씨 금지. **색만으로 정보를 구분하지 않는다** (D-day, 완료 표시는 글로도).
- **지금 할 일.** 모든 화면 위에 "지금 할 일: ..." 한 줄 (AppShell의 `todo`).
- **누르기만으로** 다 된다. 밀기, 길게 누르기, 자동으로 사라지는 시간 제한 없음.
- **모바일 우선.** 375 x 667에서 질문 화면이 스크롤 없이 보인다. 노트북에서는 가운데 최대 너비 480px.
- `lang="ko"`, 진짜 `<button>`, 키보드 포커스 표시, `prefers-reduced-motion`이면 애니메이션 끔.

## 14. 말투와 읽어 주기

- 질문과 안내는 정확한 존댓말: "~세요?", "~해요", "~주세요". 문장은 짧게, 한 문장에 한 가지.
- "~냥"은 인사, 축하 같은 감정 문장에서만. 질문에는 쓰지 않는다.
- 행정 용어는 칸 이름(옮겨 쓰는 카드, 확인 화면의 작은 글)에만 쓰고, 묻는 말은 쉬운 말로.
- 모든 화면에 "읽어 줄 말"이 있다. 소리가 켜져 있으면 화면이 열릴 때 한 번 읽고, "다시 듣기"로 다시 읽는다.
- 다른 화면으로 가거나 말하기를 시작하면 읽던 것을 멈춘다.
